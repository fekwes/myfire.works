# Review — stability, performance, scalability (July 2026)

A full pass over the app after PR #9, looking for what would break, slow down
or cost money at scale. Everything below was measured or reproduced, not
inferred; where a number appears, the method is stated so it can be re-run.

Findings are split into **fixed on this branch** and **recommended**, each
ordered by value. The recommended ones are deliberately not done: they are
product or dependency decisions, not defects.

---

## Fixed on this branch

### 1. "Signing up saves your plan" could never work on this project

**Severity: high** — the feature was silently absent for every user.

The save was attempted at the `signUp()` call, reading `data.session`. That
session only exists when the Supabase project has email confirmation **off**.
This project has it on:

```bash
curl -s "$NEXT_PUBLIC_SUPABASE_URL/auth/v1/settings" -H "apikey: $ANON" | grep autoconfirm
# "mailer_autoconfirm": false
```

So `signUp` returns no session, the insert never ran, and nothing said so. The
user then confirms by email, lands back signed in through `/auth/callback`, and
by then there is no sign-up handler left to do it.

Fixed by keying the decision off "a session now exists" rather than "a sign-up
just returned one". `lib/plan-sync.ts` holds the policy; `PlanProvider` owns the
I/O. Works for confirmation-on, confirmation-off and plain sign-in alike.

### 2. Silent write and read failures on the profiles path

**Severity: high** — the failure mode this codebase has already been bitten by
(§8.4 of the handoff).

- PostgREST *returns* its errors rather than throwing, so the `try/catch` around
  the sign-up insert caught nothing.
- `PlanProvider`'s restore read discarded `error`, so a permission failure showed
  a signed-in user the blank defaults — indistinguishable from their data being
  thrown away.
- `createProfile` trusted `.single()` to have returned a row, flashing a success
  tick when it hadn't.
- Read and delete failures were both described as failed *saves*.
- A missing table reported by PostgREST (`PGRST205`, the code a caller actually
  sees when the migration was never run) fell through to the raw message.

### 3. A saved plan reached the engine unvalidated

**Severity: high.** `sanitisePlanInput` guarded localStorage and share links —
the handoff calls it "one shared validator" — but a row's `inputs` is a `jsonb`
blob and went straight to the engine. One row written by an older build renders
`£NaN` across the projection, or worse a quietly wrong figure.
`parseProfileRows` now routes every row through the same validator.

### 4. A crafted share link could take down the recipient's tab

**Severity: high** — plans are shareable, so this is a link one person can send
another.

`sanitisePlanInput` checked that numbers were *finite*, not that they were
*plausible*. The engine builds an object per year from `currentAge` to
`lifeExpectancyAge`:

| `lifeExpectancyAge` in the link | timeline entries built |
|---|---|
| before | 5,000,001 |
| after | 121 |

Fixed with ranges by field kind (ages 0–120 and whole, money 0–1e12, rates
−90%…+100%, fractions 0–1), plus caps on a holding's fee, weight, label length
and count. In the shared validator, so links, localStorage and saved rows are
all covered at once.

### 5. Monte Carlo compared the three strategies on different market paths

**Severity: medium-high** — it produced a visibly wrong answer.

The strategies shared one generator and consumed it in turn, so each was scored
on a different set of paths. Guardrails only ever spend *less* than flat does, so
on identical paths a wider band cannot do worse than a narrower one — an
ordering that must hold exactly. It didn't:

```
seed 99999, 50 sims:  guard5 = 1.00,  guard10 = 0.98
```

The app was reporting ±10% guardrails as worse than ±5%. Now every path is drawn
once and all three strategies run over the same ones (common random numbers),
which also does a third of the random-number work.

### 6. A blocked caller could drain the global AI budget

**Severity: medium** — a one-IP flood could take the AI features down for
everyone, all day.

Both AI routes evaluated all three rate limiters on every request, and
`check()` *consumes* from its window. So a caller already blocked by the
per-minute limit still spent a token from the global 500/day backstop — the
exact outcome that backstop exists to prevent. `checkInOrder` short-circuits.

### 7. Upstream error text was returned to the browser

**Severity: medium.** Both AI routes passed the provider's error message
straight to the client, which can carry quota details, project identifiers and
model internals. A missing key also named the secret (`GEMINI_API_KEY is not
configured`). Now logged server-side, generic to the client, and a missing key
is a 503 (deliberate state) rather than a 500.

### 8. An oversized CSV froze the tab

**Severity: low-medium.** `FileReader` read any size into memory and into a
controlled `<textarea>` before the server could reject it. Capped at 512 KB with
a truncation notice.

### 9. Three copies of the asset-class list

**Severity: low, but a bug generator.** The valid classes were hand-maintained
in `lib/assets.ts` (as a type), `lib/plan-storage.ts` and the import route.
Adding a class to two of three doesn't fail to compile — it silently drops every
holding that uses the new one. Now one `ASSET_CLASSES`, with the type derived
from it. This matters more than it looks: per-country asset classes are on the
roadmap.

### 10. Middleware ran where there was no session to refresh

**Severity: low (latency and quota).** It calls `auth.getUser()` — a network
round-trip to Supabase for a signed-in visitor — and the matcher covered
everything but static assets. Both AI routes, `robots.txt`, `sitemap.xml`, the
OpenGraph image and `/auth/callback` each paid for a refresh none of them reads.
Narrowed; the 21 path cases were checked against the regex.
`api/account/delete` stays in, because it authenticates its caller.

### 11. Workspace root misdetected

**Severity: low, but deployment-affecting.** A stray `package-lock.json` in the
developer's home directory made Next infer `/Users/alberto` as the workspace
root and warn on every build. That inference drives output file tracing, which
decides what lands in the serverless functions. Pinned via
`outputFileTracingRoot`.

## Measured and deliberately not changed

Worth recording so they aren't "optimised" on a hunch later.

**The engine is not slow.** `simulateFire` is **0.04 ms**; a 2,000-path Monte
Carlo is **45 ms** (Node, this machine, mean of repeated calls). Neither needs a
web worker, and the existing `setTimeout` yield before the Monte Carlo run is
enough to paint the loading state.

**Lazy-loading the charts makes it worse.** Tried and reverted, with numbers:

| Approach | /planner initial | after visiting all tabs |
|---|---|---|
| static imports (current) | **359 KB** | 359 KB |
| all three via `next/dynamic` | 367 KB | **477 KB** |
| only `ConfidencePanel` dynamic | 367 KB | 371 KB |

Splitting costs ~8 KB of chunk overhead, and deferring all three duplicates
Recharts into a second chunk. One shared chunk is the smaller answer. A comment
in `FireDashboard` records this so it isn't retried.

## Recommended, not done

### R1. Rate limiting is per-instance, so the global cap isn't global

**Correction to an earlier draft of this document, which called this "the one
with a bill attached". There is no bill: the Gemini key has no billing enabled,
so it is on the free tier.** The exposure is availability, not cost.

`createRateLimiter` holds its counts in a per-process `Map`. On Vercel every
serverless instance has its own, so the "global 500/day" backstop is really
*500 × concurrent instances*, and it resets on every cold start. The app's own
cap therefore cannot be relied on to keep usage inside the free tier's daily
quota.

What actually happens when that quota runs out: Google starts refusing requests,
the route logs the error and returns a generic 502, and **both AI features stop
working for everyone until the quota resets** — including for the person the
portfolio piece is being shown to. One person hitting refresh, or a crawler
finding the endpoint, is enough.

Two things worth doing, in order:

1. **Handle quota exhaustion distinctly.** ✅ **Done.** Both AI routes now
   detect a 429 / `RESOURCE_EXHAUSTED` (`lib/ai-errors.ts`, unit-tested) and
   return a distinct 429 with "hit today's limit — try again tomorrow", instead
   of the generic 502 "unavailable" that read as a transient bug.
2. **Share the counter** (Upstash Redis or Vercel KV behind the existing
   `RateLimiter` interface — it was designed for exactly this swap) and set the
   global cap below the free-tier daily quota, so the app self-limits before
   Google does.

Neither is urgent in the way a bill would be, which is worth knowing before
spending an afternoon on it. If billing is ever enabled, this jumps straight
back to the top of the list.

### R2. Recharts is a third of the payload

/planner ships **359 KB** of gzipped JS, and roughly **124 KB** of it is
Recharts. The three charts are a stacked area, a bar chart and a percentile fan
— and `LandingHeroPreview` already draws a good-looking chart in plain SVG with
no library at all. Replacing Recharts in those three components would cut the
main screen's JS by about a third. It is real work (axes, tooltips,
responsiveness, the validated colour ramp) but it is bounded, and the design
system's chart rules are already written down in `docs/DESIGN.md`.

### R3. Nothing reports errors

`app/error.tsx` catches render failures and shows a friendly page, but nothing
is recorded, so a crash on someone's phone is invisible. Speed Insights is
already wired; adding error reporting alongside it is small. Keep it cookieless
so `/privacy` stays honest.

### R4. CGT is computed before the year's SIPP income is known

In `simulateFire` the drawdown order is ISA → GIA → SIPP, and the GIA's
`remainingBasicBand` is derived from `otherTaxableIncome` only — it can't see the
SIPP withdrawal decided later in the same year. When both draw heavily this
understates CGT. It is a modelling simplification rather than a bug, but it
isn't documented as one: it belongs on `/methodology` and in
`docs/ARCHITECTURE.md`, or fixed with a second pass over the year. ✅
**Documented** in both places; the second-pass engine fix remains optional.

### R5. No end-to-end regression net

Already item 7 in the handoff backlog, and the review reinforces it. Every bug
in §8 of the handoff was invisible until measured, and three of the findings
above (the sign-up flow, the restore path, the share-link hang) are only
reachable through the browser. Playwright over the seeded-state sweeps would
catch the class, not just the instances.

### R6. `api/account/delete` is unmetered

It authenticates its caller, so the exposure is small, but it is the one
irreversible endpoint in the app and it has no rate limit. ✅ **Done** — a per-IP
8/min cap now backstops it, using the existing limiter.

## What still needs a human

Two things could not be verified from here, and both need someone who can hold
an account:

1. **The signed-in profile flows against live Supabase.** Creating accounts and
   entering passwords is out of scope for an agent. The exact click-through is
   in `docs/HANDOFF-FIREWORKS.md` under Known Gaps. What *was* verified without
   an account: the `portfolios` table exists and `anon` is correctly denied
   (`42501`, not a missing-table error), and email confirmation is on — which is
   what surfaced finding 1.
2. **Gemini's classification quality.** Everything else about the import is now
   covered by tests; `npm run smoke:ai-import` against a dev server with a real
   key prints what the model made of four realistic pastes — including a prompt
   injection hidden in the pasted document — and flags misclassifications.
